# TermX · 信任模型与安全边界

本文件明示当前版本的安全设计取舍，供部署者评估威胁模型（对应安全审计 H1/M1 项声明）。

## 三层信任边界

| 边界 | 保护能力 | 说明 |
|---|---|---|
| **网络攻击者**（未持凭据） | ✅ 完全防护 | 接口鉴权、限流、CORS、验证码、锁定退避、引导面同源绑定 |
| **磁盘窃贼**（拖走 data/ 整个目录） | ⚠️ 部分 | 主密文（密码包裹）不可解；但 TermX 同步副本（termx_secret）可由目录内材料派生密钥解开——见下 |
| **服务器本体沦陷**（RCE/内存读取） | ❌ 无防护 | 运行期服务器持有库密钥（登录解包入内存、登录响应下发 data_key），reveal/export/import 与 TermX 双向翻译均需服务端解密 |

## 已知取舍（有意设计，非疏漏）

1. **TermX 深融合**（对应 termx_secret 列）：为让 Web 端可编辑 TermX 客户端同步的条目，
   服务器持两把密钥材料做双向翻译。代价：拖走完整 data/ 目录可解全部凭据。
   如需彻底零知识，需撤销服务端翻译并把导出/导入改为纯客户端加解密（规划中）。
2. **运行期信任**：登录响应下发 data_key 供浏览器本地解密（前端加密链的根）；
   服务端内存常驻库密钥。HTTP 明文部署下该密钥可被同网段嗅探——请启用 HTTPS。
3. **手写 JS 密码学**（utils/crypto.js）：因 HTTP 非安全上下文无 crypto.subtle 而手写
   AES-256-GCM/SHA-256，已通过 NIST 测试向量自检；HTTPS 后应迁移 crypto.subtle。

## 部署建议

- 生产启用 HTTPS（安装引导服务设置步）
- 使用强主密码（包裹密钥的强度上限=密码强度）
- 服务器磁盘/系统本身的加固属部署者责任（data/ 已 0600）
